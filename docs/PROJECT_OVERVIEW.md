# 炮炮签到站：项目逻辑与发展方向

更新时间：2026-07-09

## 1. 项目目标

炮炮签到站（Paopao Checkin Manager）是面向普通用户的网页签到管理器。它不是某一个网站的专用脚本，而是把“登录、识别签到入口、安全执行、记录结果、发送通知”抽象成可配置流程。

项目首先保证安全和可恢复，其次才追求识别范围：页面状态不明确、出现验证码、入口存在歧义或执行结果无法确认时，应停止并留下证据，不猜测点击，不尝试绕过验证。

核心使用方向：

- 用户可以添加多个签到任务，并复用系统预置骨架或维护自己的模板。
- 普通账号密码网页使用浏览器流程；适合接口化的网站可使用 HTTP/HAR 流程。
- 验证码由用户在人工登录窗口处理，成功会话加密保存并供正式任务复用。
- 自动识别不可靠时，用户可以用元素选择模式明确指定签到入口。
- 用户可以自行维护签到文字、选择器、代理、通知和清理策略，不依赖修改源码。

## 2. 当前实现逻辑

```text
管理页面
  -> Fastify API 与登录保护
  -> SQLite（任务、模板、会话、队列、运行记录、通知和设置）
  -> 定时器 / 手动运行
  -> 单 Worker 队列
  -> 执行引擎
  -> 浏览器表单适配器 或 HTTP 流程适配器
  -> 会话、代理、安全检测、结果确认
  -> 运行记录、截图与通知
```

代码由两层组成：

- 根目录 `src/`：通用 Playwright 执行内核，负责登录、签到检测、安全停止、重试和基础通知能力。它仍被生产镜像构建并动态加载，不是旧代码。
- `app/`：正式管理应用，包括 React 页面、Fastify API、SQLite 数据库、模板、队列、会话、人工登录、HAR 导入、清理和通知管理。

主要实现手段：

- 登录后默认进入运行总览，以状态摘要、待处理事项和当前任务列表直接呈现今日计划、异常、有效会话与下次执行时间。
- 下次执行时间按任务时区和真实日历计算，覆盖跨日与夏令时跳变，不再使用固定“明天”文案。
- 添加和编辑任务使用三步向导，逐步完成目标模板、账号识别、计划通知，并在最终保存前提供摘要。
- 页面采用统一的浅色、深色设计令牌和响应式壳层；移动端使用顶部栏与抽屉导航，账号入口只保留在右上角。
- 所有普通用户资源带所有者标识，API 同时按角色、所有者、能力开关和配额强制校验；页面隐藏不是安全边界。
- 主密码账号是唯一主管理员，可配置注册、角色和默认权限；运营管理员只负责日常用户与异常处置，不能读取秘密或代用户执行。
- 队列串行执行并对同一任务去重，人工登录占用浏览器时任务继续排队。
- SQLite 版本化迁移；账号、密码、Cookie 和通知密钥加密保存。
- 浏览器会话先验证后复用，失效时再回到登录流程。
- 签到入口依次使用明确 CSS、用户词库、可访问属性和受控语义属性识别；多候选时停止。
- 人工元素选择只定位和高亮，不向目标网页发送点击，用户二次确认后保存选择器。
- 运行结果保留状态、阶段、耗时、脱敏信号和必要截图；按时间与容量双条件清理。
- 代理支持系统继承、任务专用和直连，并持久化最近检测结果。
- 通知按任务策略发送，通知失败不会覆盖签到本身的真实结果。

## 3. 已遇到的问题与形成的原则

- 项目治理原则：健壮性、简洁度和长期可维护性优先于短期表面修复。本地部署、正式部署、设计、功能修改和未来规划都应避免临时补丁式方案；当小问题暴露出结构性缺陷时，应优先同项目所有者沟通源头方案，而不是用页面级特判、重复配置或隐性覆盖绕过去。
- 实施原则：优先在源规则、公共抽象、数据模型、执行流程和发布流程中修复根因；只有在确认风险和收益后才接受局部兜底，并需要记录原因、范围和后续清理条件。
- 登录页视觉不能只按单一桌面宽度判断。宽屏下要同时检查整体重心、小猪/装饰图与表单的关系，避免卡片贴边、装饰压边或局部元素抢占标题层级。
- 小猪状态图属于登录卡片的辅助品牌视觉：允许保持较大尺寸，但必须落在明确留白中，不能挤压标题、输入框、按钮或移动端安全区域。
- 表单行内按钮必须有稳定网格间距；输入框与按钮不得共用边线或贴边，窄屏下要自然换行。
- 状态颜色必须按语义统一：成功用绿色，明确失败/直接错误用红色，待处理、需要验证、取消、页面变化、已签到等非成功状态用黄色或警示色；不要让普通正文色承载状态含义。
- 深色模式不能只反转页面背景。输入单位后缀、提示框、预览卡、状态卡、标签按钮等局部容器都必须使用主题 token，禁止残留白色块或浅色断层。

- 普通说明文字曾被误判成验证码。现在以明确验证码组件和交互状态为主，页面普通文字不能单独触发判断。
- 页面初始按钮与接口状态存在异步竞争，曾导致重复签到风险。现在优先读取明确接口或稳定 UI 状态，并保持幂等。
- 人工登录和正式执行曾像两条路径。现以任务会话为共同状态，人工处理完成后由正式执行路径验证并复用。
- 图片按钮可能没有可见文字。当前结合 `alt/title/aria-label/id/class/href/src` 的受控语义识别，并用人工元素选择兜底。
- 单站名称曾进入预置模板，造成“通用模板像站点特例”。预置模板现在按网页结构和用途命名。
- 预置模板与用户模板曾混在一起，且复制后才能建任务。现在分表管理，直接选预置模板保存任务时自动生成任务专用模板。
- 原生确定/取消弹窗、说明文字过多、第一人称文案影响理解。界面方向是短说明、明确动作、统一自有弹窗和非技术表达。
- 代理曾长期显示“已配置但未检测”。现在保存检测时间与结果，配置变化后才回到待检测状态。
- 截图和运行记录曾缺少容量治理。现在支持天数、容量上限、使用量监视和手动清理。
- 早期项目存在 `demo`、站点专名和不连续版本。现已统一正式名称，并建立版本同步规则。
- Windows 本地曾混用 npm/pnpm，导致原生依赖不可用。项目以 `package-lock.json` 和 npm 为唯一依赖基线，验证以隔离 Docker 构建为准。

## 4. 用户需求方向

- 面向普通用户，不要求理解适配器、选择器、Webhook 等内部术语。
- 页面文字要少而有效；帮助应靠近具体输入项，并说明去哪里取得 Key、Webhook 或 HAR。
- 通用经验优先，禁止把某个站点的元素 ID、名称或行为直接包装成“通用能力”。
- 自动识别与用户配置并行：系统提供安全默认值，用户可以维护词库、选择器和模板。
- 验证码不自动破解；允许第一次由用户处理，并尽量让后续任务安全复用同一会话。
- 预置能力是起点，保存任务时自然形成可维护的用户模板，不要求用户绕到另一个页面先复制。
- 错误证据必须可查看且可清理，存储状态应在设置中可理解、可监视。
- 所有正式执行变化都应分阶段启用、可检查、可回退，不直接破坏已稳定的线上路径。

## 5. 未来可构建方向

当前 `0.7.0`：

- 日间、夜间、跟随系统三种主题，覆盖登录页、管理页、弹窗和移动端。
- 支持普通用户注册登录，并保留现有管理员主密码入口；默认先显示用户登录。
- HAR 导入已并入新建模板弹窗，旧地址保持兼容。
- 普通用户资源已隔离，并受账号能力开关、任务配额和每日操作配额限制。
- 主管理员管理注册、角色和最高权限；运营管理员处理用户、异常任务、会话、运行记录和模板审核。
- 正式环境采用邀请注册；浏览器表单模板可投稿审核，HTTP Flow 不公开共享。
- 数据库迁移至 v12，现有管理员凭据、任务、运行记录、会话和通知完整归属主管理员。
- 运行总览、真实下次执行时间、分步任务向导、精简导航和响应式视觉系统已正式上线。

后续方向：

- 任务与模板导入导出、备份恢复和迁移检查。
- 更清晰的执行诊断：阶段时间线、失败分类、会话有效期和存储趋势。
- 模板能力分级与兼容性检测，形成可测试、可升级的通用适配器规范。
- 在确有并发需求后，再评估多 Worker、分布式队列和独立浏览器执行节点。
- 2FA、邮件找回和团队空间只在有明确身份与协作需求后评估；当前不扩大账号体系。

明确不做：自动破解验证码、在状态不明确时模糊点击、把敏感凭据写入日志或导出文件。

## 6. 构建与发布约束

- npm 与 `package-lock.json` 是唯一依赖基线，不提交 `node_modules`、`dist`、缓存或本地数据库。
- 生产镜像必须在构建阶段通过完整测试与前后端构建。
- 数据库迁移只向前执行；部署前备份数据库和密钥，保留可验证的旧镜像。
- 部署前检查活动 Job；切换时不得让新旧调度器同时运行。
- 发布后检查容器健康、重启次数、HTTPS、任务数量、会话状态、数据库版本和错误日志。
- 不以真实签到作为普通回归测试；优先使用模拟模式、测试夹具、只读检查和隔离构建。

版本与线上状态分别管理：只有形成可部署的线上产品变化时才按规则更新项目版本；本地清理、说明和协作记忆不升级。只有任务明确包含部署时，才更新正式容器。
